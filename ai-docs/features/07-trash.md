# 回收站

> 已实现。对应 `src/logic/store/mails.ts` 的回收站一节、`src/options/pages/TrashPage.vue`、
> `MailListItem.vue` 的时间/垃圾桶叠放，以及 `AppSettings.autoDeleteExpiredCode`。

## 1. 一句话

**两种「删除」是两件事**，这个区分是整个设计的地基：

| 用户动作 | 底层 | 可撤销 |
| --- | --- | --- |
| 弹窗里把鼠标移到**卡片**上 → 点右上角垃圾桶 | **状态变更**（往邮件上写一个 `trashedAt` 时间戳） | ✅ 能在回收站里一键恢复 |
| 回收站里点「彻底删除」/「清空回收站」 | **硬删除**（`objectStore.delete`） | ❌ 没有撤销 |

### 为什么不做软删除

回收站本身**已经**是软删除层了。在它下面再叠一层（比如 `deleted: true` 标记）
只会让「彻底删除」名不副实 —— 用户以为空间被释放了，其实记录还在库里。
所以「彻底删除」就是 `del('mails', id)`，没有中间态。

### 为什么用时间戳而不是布尔量

`trashedAt?: number` 而不是 `trashed: true`，两个理由：

1. **回收站要按删除时间倒序**（最近删的在最前），而且要显示「什么时候删的」——
   布尔量表达不了；
2. **IndexedDB 的索引不收录字段缺失的记录**。所以 `by-trashedAt` 索引天然
   只包含「在回收站里」的邮件，拿它的游标倒序遍历就是回收站列表 ——
   不需要全表扫再过滤。
   布尔量做不到这一点：IndexedDB 没有「部分索引」，`by-trashed`（`true`/`false`）
   会把所有邮件都收进去。

判据仍然是便宜的 `!!mail.trashedAt`。

## 2. 数据层

`DB_VERSION` 从 1 升到 2，新增索引 `mails.by-trashedAt`。

```
⚠ upgrade() 里必须是 `else if (oldVersion < 2)`，不是独立的 `if`。
  全新安装时 oldVersion === 0，第一个分支已经把 STORES 里的索引全建好了
  （STORES 是当前结构的唯一真相，已含 by-trashedAt）。此时再 createIndex 会抛
  ConstraintError，而 onupgradeneeded 里的异常会让整个升级事务 abort ——
  表现是 AbortError、库根本打不开，错误信息完全不提索引重名。
```

操作：

| 函数 | 作用 |
| --- | --- |
| `trashMail(id, at?)` | 移入回收站（`trashedAt` 已有值则**保留原值**） |
| `restoreMail(id)` | 恢复（删掉 `trashedAt`） |
| `readTrashedMails(limit)` | 回收站列表，按删除时间倒序 |
| `countTrashedMails()` | 回收站条数 |
| `deleteMailForever(id)` | **硬删除**一封 |
| `emptyTrash()` | **硬删除**全部（单事务） |
| `trashExpiredCodes(graceMs, now)` | 失效验证码批量入回收站 |

`trashMail` 保留原来的 `trashedAt`：否则重复点删除会把邮件的排序位置一直往前顶，
用户会看到「这封怎么突然跑到最上面」。

## 3. 三条必须守住的不变量

### 3.1 移入回收站不丢字段

只加一个 `trashedAt`（并顺手置 `read: true` —— 它已经离开主列表，
留着「未读」只会让 badge 与状态对不上），**其余字段一律不动**。
正文、`ai`、`code`、`codeExpiresAt` 全在 ——
所以恢复是零成本的，也是**无损**的。（测试里专门断言了这一点。）

### 3.2 滚动淘汰**不碰**回收站

这是最容易在重构里被顺手破坏的一条。`pruneMails` 原来的逻辑是
「数整表条数、删最旧的 N 封」—— 回收站里的会被一起数进去、一起删掉。

后果：回收站变成一个「过一会儿自己清空」的假回收站，用户来不及反悔。

现在：

- 计数只算 `trashedAt === undefined` 的（回收站**不占保留名额**，
  否则用户会看到「上限 100，主列表只剩 60 封」而不知道那 40 封在回收站里）；
- 淘汰游标跳过回收站里的条目；
- **代价**：回收站会一直占空间。这是有意的 —— 占用是**可见**的（回收站页有计数），
  而「东西悄悄没了」是不可见的。前者用户能处理，后者不能。

### 3.3 回收站里的邮件不进主列表

过滤放在 `readRecentMails` / `readMailsByAccount` **内部**，而不是让每个调用方自己滤。
它们是 Popup / Sidepanel / badge / `markAllRead` 的共同入口，
漏掉任何一处都会让「已删除的邮件」在某个界面里冒出来。

⚠ 顺序有讲究：**先归一化再判断**。归一化会清掉未知字段，
在它之前读 `trashedAt` 读到的是原始数据（形状可能不对）。

## 4. 失效验证码自动删除

`AppSettings.autoDeleteExpiredCode`，**默认开启**。

规则：验证码邮件的 `codeExpiresAt` 到了之后**再等 30 秒**，移入回收站。

### 为什么是 30 秒而不是立刻

`codeExpiresAt` 是**推算**出来的（`receivedAt` + AI 读到的时长），
本身带几十秒误差：投递延迟、模型对「5 分钟」这类表述的取整。

立刻删会在边界上误删**其实还有效**的验证码 —— 而验证码是一次性的，
误删等于用户要重新申请一个。30 秒宽限期把这类误差盖住，
代价只是回收站里多躺半分钟。

### 为什么用 alarm 而不是 setTimeout

```
⚠ MV3 的 Service Worker 空闲约 30 秒就被回收，而 setTimeout 不会在回收后触发。
  用它做「失效后 30 秒删除」在真机上基本永远不执行 —— 而代码看起来完全正确。
```

所以走 `chrome.alarms`（`PURGE_ALARM`，周期 1 分钟），并且挂在同步 alarm 的回调里
顺带跑一次。实际延迟落在「失效 + 30 秒 ~ +90 秒」，对本功能完全可接受。

⚠ `ensureAlarm()` 里**两个定时器各自判断各自创建**：不能因为「同步定时器已存在」
就整个函数短路 —— 老用户已经有 `SYNC_ALARM`，用它的存在性短路会让
`PURGE_ALARM` **永远建不起来**。

### 只处理有明确有效期的

`codeExpiresAt === undefined` 的**永不动它**。
「不知道什么时候失效」不等于「已经失效」—— 删掉它就是删掉一封可能还能用的验证码。

### 幂等

已在回收站里的跳过。不跳的话每轮 alarm 都会重写一遍：
`trashedAt` 被刷新（排序乱掉），还会白白触发广播。

## 5. UI

### 5.1 弹窗里的垃圾桶

鼠标进入卡片 → 卡片右上角出现**灰色**垃圾桶，同时该位置的**时间淡出**；
鼠标再移到垃圾桶上 → 变**红**；点击 → 弹确认框。

时间与垃圾桶视觉上占**同一个位置**（时间在文档流里，垃圾桶绝对定位盖在它上面），
所以两者必须**互斥**，否则会糊在一起。

#### ⚠ 显隐由状态驱动，不用 CSS `:hover` 组合

这是本节最值得记的一条 —— 真机上为此踩了三个坑，而且三个都表现为
「界面不动」，**没有任何报错**：

| 现象 | 原因 |
| --- | --- |
| 悬停卡片后时间不消失 | 时间的淡出挂在**第二个**条件（`.trash-zone:hover`）上，与垃圾桶的显示时机不一致，中间那一段两者并存 |
| 长按复制按钮，删除按钮显示；松开就隐藏 | 显示挂在 `.mail-item:hover` 上。**CSS `:hover` 在元素内部 DOM 变动后不会重新求值** —— 点复制时按钮被换成「√ 复制成功」，浏览器不重算悬停，删除按钮就跟着复制按钮的行为走了 |
| 悬停卡片后删除按钮不出现 | 显示条件被收窄成「只能悬停右上角那一小块」，而不是「鼠标在卡片里」 |

现在的做法：**一个状态值 + `mouseenter` / `mouseleave`**。

```ts
const cardHovered = ref(false)        // 卡片的 mouseenter / mouseleave
const trashZoneHovered = ref(false)   // 热区自己的 mouseenter / mouseleave
const trashZoneVisible = computed(() => cardHovered.value || trashZoneHovered.value)
```

- 垃圾桶用 `:class="{ 'is-visible': trashZoneVisible }"`
- 时间用 `:class="{ 'is-hidden': trashZoneVisible }"`

两者是**同一个布尔值**的两个镜像，所以不可能出现「一个显示了、另一个还没反应」。
`mouseenter` / `mouseleave` 由浏览器在指针真的进出时直接触发，与卡片里别处重渲染无关。

```
⚠ 不要退回「用兄弟选择器 + 另一个元素的 class」那种写法
  （`.trash-zone.is-visible ~ .time-slot .time`）。它看着等价，
  实际把判断寄托在「另一个元素的 class + DOM 顺序 + scoped 属性」三件事同时成立上，
  任何一环不对就**静默失效** —— CSS 选择器匹配失败不会报错，界面只是没变。
  实现里留了这条历史说明，`mail-list-item.spec.ts` 也有断言禁止它回来。

⚠ 热区**始终** `pointer-events: auto`，不随可见性切换。
  早期版本在隐藏时设 `pointer-events: none`（想防止看不见的按钮吃掉点击），
  但那有个致命副作用：**隐藏的元素收不到 `mouseenter`，永远没法把自己点亮**。
  至于「点右上角不该误触删除」—— 不需要挡：热区的 `mouseenter` 一触发图标就可见了，
  用户看得见自己在点删除。

⚠ 按钮要 `@click.stop`：整张卡片绑了「打开邮件」，不拦住冒泡的话
  点删除会顺手把邮件打开（那是用户最不想要的结果）。

⚠ 用**透明度**而不是 `v-if` 切换：后者会让头部这一行的宽度跳变，
  flex 布局下发件人名字会被挤得抖一下。
```

### 5.2 回收站页（设置里的一个 tab）

表格列：发件人 / 主题 / 验证码 / 删除时间 / 操作。
行内三个按钮的文案是 **恢复 / 删除 / 彻底删除**（`strings.ts` 的 `trash.restore`、
`mail.trash`、`trash.deleteForever`）—— 「删除」与「彻底删除」的区别正是本页的核心语义，
所以两个都要有（理由见下面「回收站页里为什么也有『删除』」）。
顶部有「清空回收站」和自动删除开关。

**这一页在极简模式也显示**（不在 `FULL_MODE_ONLY` 里）。理由：
自动删除默认开着，而它会把邮件移进回收站；极简模式下藏掉这一页，
用户就找不到那些自动消失的验证码了 —— 而那正是最需要回收站的时候。
提示词 / 屏蔽列表是**功能**，回收站是**数据出口**，两者不是一类。

### 5.3 删除确认弹窗

**所有删除都确认**：弹窗里的垃圾桶、回收站里的彻底删除、清空回收站。

组件是 `src/components/ConfirmDialog.vue`，Popup / Sidepanel 共用的状态在
`src/logic/trash-confirm.ts`。

### 为什么不用原生 `confirm()`

1. **它是同步阻塞的** —— 整个页面卡住（Vue 的更新也排在它后面）；
2. **无法自定义按钮文案**，而「彻底删除」这类动作值得把后果写在按钮上；
3. **样式与产品完全脱节**，深色主题下尤其突兀。

### 为什么不用「两步按钮」

试过（「清空回收站」→「再点一次，彻底删除」）。问题是**第二次点击时看不到关键信息**：
还剩几封、删掉的是哪一封，都不在眼前。弹窗可以把后果写在正文里。

### 行为约定（都有测试守着）

| 操作 | 结果 |
| --- | --- |
| 点确认 | `confirm` |
| 点取消 / 点遮罩 / 按 `Escape` | `cancel` |
| 点弹窗本体 | **什么都不做**（否则手抖点空白就关掉了，用户以为「确认过了」） |

```
⚠ 默认焦点在**取消**按钮上，不是确认按钮。
  危险操作的默认焦点必须在「不删」那一侧 —— 否则用户习惯性敲回车
  就会把邮件删掉。这是「弹窗确认」相对「两步按钮」唯一可能更糟的地方，
  所以专门补上，并有断言钉住。

⚠ Escape 监听只在 open 时挂、关闭立刻摘。常驻的话调用方会在弹窗之外
  收到莫名其妙的 cancel —— 表现为「有时候列表会自己刷新」，极难归因。

⚠ 用 v-if 而不是 v-show：隐藏的弹窗不该留在 DOM 里参与 Tab 顺序，
  否则用户按 Tab 会「跳进一个看不见的弹窗」。
```

删除确认的**文案要说出去哪儿恢复**（「可在『设置 · 回收站』里恢复」）——
只弹「确定吗」不说后果，等于白添一次点击。

### 回收站页里为什么也有「删除」

这一页显示的是**已删除**的邮件，而用户在这里也可能改主意想让它彻底离开主列表
（而不是恢复到列表里）。所以行内三个按钮：恢复 / 删除 / 彻底删除 ——
「删除」与「彻底删除」的区别正是本页的核心语义。

「标记已读」那种可逆且无后果的动作**不**确认 —— 弹窗只会让人烦。

### 5.4 垃圾桶图标的位置

图标在**卡片右上角**，与**时间的右边缘重合**，所以两者切换时右边不会跳（用户报过「割裂」）。

```css
.mail-item { padding: 10px 12px; position: relative }   /* 定位祖先 + 内边距 */
.trash-zone { position: absolute; top: 8px; right: 12px; width: 18px; height: 18px }
```

数值都是按内边距反算的，不是随手填的：

| 值 | 来历 |
| --- | --- |
| `right: 12px` | ＝ 卡片的 `padding-right`。时间在文档流里，右边缘距内容区正好 12px；垃圾桶是绝对定位的，所以要把 `right` 设成同一个数，**两个右边缘才重合** |
| `top: 8px` | ＝ `padding-top - (热区高 - 时间行高) / 2 = 10 - (18 - 14) / 2` |

```
⚠ 不要按「让图标**中心**对齐时间右边缘」去算（那会得到 `12 - 18/2 = 3px`）——
  那是另一种对齐，效果是图标整体往里缩、看起来被挤到中间。
  用户要的是「图标右侧位置在文字右侧」：两个**右边缘**在同一条竖线上。

⚠ 三个数（卡片 padding、热区宽高、这两个偏移）必须一起改。
  `mail-item-style.spec.ts` 里断言的是**关系式**（`right === paddingRight`，
  **零容差**）而不是写死的数值 —— 改了内边距而忘了偏移，测试会立刻失败。
  早期那条断言给过 2px 容差，结果把 `right` 改成贴边的 `2px`
  （与时间差 4px，正是「割裂」）时**照样通过**，等于没在守。

⚠ 配色分两步：进卡片是**灰**的，移到图标**上**才变**红**。
  一出现就红会让整个列表显得很吵，红色是「危险动作」的信号，
  只在用户真的瞄准它时给。

⚠ 定位与尺寸写在 scoped 样式里，不用 UnoCSS 工具类：
  `.trash-zone` 编译成 `.trash-zone[data-v-xxx]`（特异度 0,2,0），
  而 UnoCSS 的 `.absolute` 是 0,1,0 —— scoped 一定赢，
  混着写会变成「工具类看着生效了其实被覆盖」。
  所以：布局在 scoped，**图标本身**用 UnoCSS（`i-pixelarticons-trash`）。
```

### 5.5 复制按钮的反馈

验证码那一行的「复制」是**文字按钮**（无边框、无底色），
点成功后变成绿色的「√ 复制成功」，**3 秒后自己变回「复制」**。

```ts
const justCopied = ref(new Set<string>())   // src/logic/copy-feedback.ts
export const COPY_FEEDBACK_MS = 3000
```

```
⚠ 这个状态**不落库**，也**不复用 `Mail.copyStatus`**。
  `copyStatus` 是持久字段，只由「自动复制」流水线写（收到验证码时后台帮用户复制了）。
  两者混用时会互相覆盖，真机现象是「点完复制，成功提示永远不消失」：
    点击 → 本地标 'copied' → 让后台落库 → 后台广播 mail:updated →
    reload() 把 mails.value 整个换成从库里读回来的新数组（还是 'copied'）→
    3 秒后定时器改的是**已经被换掉的那个旧对象** ⇒ 界面不变。

⚠「复制」按钮本身在**弹窗/侧边栏自己**写剪贴板，不由 background 代劳：
  writeText 要求调用方是 focused 文档，而 Popup / Sidepanel 正是；
  交给 background 的话它只能降级去打「当前激活 tab 的 content script」，
  而用户点弹窗时激活页往往就是扩展自己的页面（没有 content script），
  消息石沉大海 —— 那正是「复制按钮无效」的成因。

⚠ `Set` 的增删**不触发** Vue 响应式（ref 只追踪 .value 的整体替换），
  所以每次都要 `.value = new Set(...)`。就地 .add() 的话界面不会重渲染 ——
  而「几秒后复原」那些断言**照样通过**，所以专门有一条断言盯
  「.value 换了新对象」。

⚠ 复原是必需的：用户可能有**两个**验证码要复制，
  第一封永远停在成功态会让他分不清哪封是刚点过的。
```

### 5.6 一条贯穿的规矩

卡片上所有显隐（垃圾桶、时间、复制成功）**一律由 class 状态驱动**：

```
状态是唯一真相，CSS 选择器不参与判断。
```

理由见 5.1 —— 用选择器表达「A 显示时 B 隐藏」的每一次尝试都产生了
「界面不动、但没有报错」的 bug。

- `mail-item-style.spec.ts` 管「**长什么样**」—— 解析 `<style scoped>`，断言声明；
- `mail-list-item.spec.ts` 管「**什么时候出现**」—— 挂真组件、派发真 `mouseenter`。

数据层覆盖：

- 移入 / 恢复 / 硬删除 / 清空的基本行为
- **移入回收站不丢字段**（正文、`ai`、`code`、`codeExpiresAt`）
- 重复移入保留第一次的时间
- 回收站列表按删除时间倒序、`limit` 生效
- **30 秒宽限期的边界**（刚好越过就该动手、还在期内不动）
- 没有 `codeExpiresAt` 的永远不自动删
- 已入回收站的不被重复处理（`trashedAt` 不刷新）
- **滚动淘汰不碰回收站**、回收站不占保留名额

交互覆盖（那些「界面不动、但不报错」的 bug 全在这里）：

- 鼠标进卡片 → 垃圾桶出现**且**时间让位（同一个状态）
- **点复制不影响删除按钮的可见状态**
- 点复制之后删除按钮的 **DOM 节点没被重建**（`isSameNode`）
- 禁止 `.mail-item:hover .trash-zone` 与兄弟选择器回来
- 复制反馈**过了 `COPY_FEEDBACK_MS` 自动复原**、多封各自计时、
  重复点会重新计时、卸载后定时器不再改状态
- 弹窗：默认焦点在取消、三种取消路径（按钮 / 遮罩 / Esc）、
  点本体不关、关闭后 Esc 不再触发、`danger` 的按钮配色

三条踩过的坑记在这里：

```
⚠ 种子数据要用 `upsertMail(mail, 'unlimited')`：不给这个 override 的话，
  upsertMail 自己就会按默认上限边写边淘汰，种子还没铺完就被削到上限，
  后面那次 pruneMails 自然无事可做 —— 测试会以「removed 是 0」的形式失败，
  看起来像产品 bug，其实是测试自己没造出超限状态。

⚠ `AppSettings.mailRetention` 只接受 {100, 200, 500, 1000, 'unlimited'}
  （RETENTION_VALUES），设不成小值。所以淘汰那两条用例直接调
  `pruneMails(ctx, LIMIT)`（它的契约接受任意 RetentionLimit），
  而不是绕 patchAppSettings —— 否则会得到「设了 2 却变成 100」的假失败。

⚠ 断言「某条 CSS 声明**不**存在」时必须先**剥掉注释**。
  本项目习惯在注释里写「早期版本设过 `pointer-events: none`」这类反向说明，
  正则会把它一起匹配上，于是得到假失败：代码是对的，测试却说错了。

⚠ 容差一旦放宽就守不住东西。样式契约最初给 2px 容差，把 `right` 改成
  贴边的 `2px`（差 4px，正是用户报的割裂）时照样通过。
  两个值本来就该相等时，用 `toBe` 而不是 `toBeCloseTo`。
```
