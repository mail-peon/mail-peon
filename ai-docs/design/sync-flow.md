# 收信流程

> 对应代码：`src/background/main.ts`（连接 / 唤醒）→ `src/background/sync.ts` → `src/adapters/mail/mailbox.ts` → `src/adapters/mail/providers/imap/`

## 核心分工

```
   ┌─────────────────────────────────────────────────────────────┐
   │  中继：持有**常驻 IMAP 连接**（IDLE），新邮件一到就推给插件      │
   │  插件：被推醒后**快速抓一轮增量**，然后继续待命                  │
   └─────────────────────────────────────────────────────────────┘
```

**为什么长连接在中继而不是插件里**：MV3 的 Service Worker 空闲约 30 秒就被回收，
`setInterval` 不可靠、常驻连接也保不住。中继是普通 Node 进程，可以 24 小时挂着
`IDLE`。而这个长连接**不需要额外信任** —— 中继为了通 TLS 本来就要终止握手，
早就看得到明文了（见 [`../decisions/adr-0005-imap-needs-relay.md`](../decisions/adr-0005-imap-needs-relay.md)）。

## 1. 整体拓扑

```
   ┌──────────────┐   ① WebSocket（连上就发 watch 请求）
   │  extension   │ ──────────────────────────────▶ ┌──────────────┐
   │  background  │                                 │    中继       │
   │  service     │ ◀────────────────────────────── │ 127.0.0.1    │
   │  worker      │   ③ 推「有新邮件」                │   :8787      │
   └──────┬───────┘                                 └──────┬───────┘
          │                                                │ ② IDLE 常驻
          │ ④ 抓一轮增量（新建一条普通连接）                  │
          └───────────────────────────────────────────────▶│
                                                    ┌──────▼───────┐
                                                    │  imap.qq.com │
                                                    │    :993      │
                                                    └──────────────┘
```

中继上有**两条不同用途的连接**，互不干扰：

| | watch 连接 | 同步连接 |
|---|---|---|
| 谁发起 | 插件连上中继时 | 每次抓取时新建 |
| 生命周期 | 常驻（跨多次收信） | 用完就关 |
| 传什么 | 只传「有几封新邮件」这类事件 | 完整的 IMAP 命令与邮件正文 |
| 代码路径 | `startWatch()`（中继自己解析 IMAP） | 纯字节透传（原来的路径） |

## 2. 中继的 watch 状态机

```
   收到 watch 请求 {__watch:1, accountId, host, port, tls, user, pass, token}
              │
              │  ⚠️ 这些字段是**不可信输入**：中继侧把 host/port/user/pass
              │     一律当 unknown 收下，再 String() / Number() 转换 ——
              │     转换那一层就是信任边界（见 relay 的 isWatchRequest）
              ▼
              ▼
       连 TCP + TLS
              │
              ▼
   ← * OK [CAPABILITY …]            （问候语里有 EXISTS 就不算，见下）
   → A0001 LOGIN "user" "pass"
   ← A0001 OK
   → A0002 SELECT INBOX
   ← * 35497 EXISTS                 ★ 这是**基准值**
   ← A0002 OK [READ-WRITE]
              │
              ▼
   ┌──────────────────────────────────────────────┐
   │  → A0003 IDLE                                 │
   │  ← + idling                                   │
   │                                               │
   │  …… 静默等待，服务器有新邮件时主动推 ……        │
   │                                               │
   │  ← * 35498 EXISTS        ★ 比基准大 → 有新的   │
   │       │                                       │
   │       └──▶ 推给插件：{"type":"mail","exists":…}│
   │            基准值 = 35498                      │
   │                                               │
   │  ← * 35499 EXISTS        ★ 再来一封，再推一次   │
   │                                               │
   │  每 25 分钟（RFC 2177 建议 ≤29 分钟）：         │
   │    → DONE  ← A0003 OK                         │
   │    → A0004 IDLE   （重新挂上，防止服务端断）    │
   └──────────────────────────────────────────────┘
              │
              │ 连接断了（网络 / 服务端 / 超时）
              ▼
       退避重连 2s → 5s → 15s → 30s → 1m → 2m → 5m
       期间推 {"type":"state","state":"reconnecting"}
```

**只认 `EXISTS` 变大**，不看 `RECENT`：

`RECENT` 的语义在 RFC 里是「本次会话期间到达的邮件数」，不同服务器实现差别很大
（QQ 在 `SELECT` 时经常直接给 `* 0 RECENT`，哪怕明明有新邮件）。而 `EXISTS` 是
「邮箱里现在共有多少封」—— 它变大就等于「有新邮件」，语义干净且所有服务器一致。

**基准值取 `SELECT` 那一刻的 `EXISTS`**：

这样「插件连上之前刚到的那封」不会被误推成两次；而它本来也不会丢 ——
插件被推醒后做的是一轮正常的增量抓取，抓的是**游标之后的所有邮件**，
不依赖推送里带的数字。

## 3. 插件侧：被推醒后做什么

```
   中继推来 {"type":"mail"}
              │
              ▼
       worker 被唤醒
              │
              ▼
   走**同一条** runSyncCycle 路径
   （手动「立即同步增量」用的也是它）
              │
              ▼
   收信 → 解析 → AI → 入库 → 角标 / 提示
              │
              ▼
       回到待命（连接保持）
```

⚠️ **关键设计**：推送里**不带邮件内容**，只带「有新邮件了」这个事实。

两个理由：

1. 插件侧只需要**一个**代码路径 —— 无论触发者是推送、手动点击还是兜底定时器，
   都走 `runSyncCycle`。多一条「推送专用抓取」的路，就等于多一个
   「只有推送时才复现」的 bug 温床。
2. 中继不必解析邮件。它对邮件内容的了解**仅限**「有几封」，
   连主题都看不到 —— 这是刻意的：中继越笨，它出问题时的破坏面越小。

## 4. 一轮同步内部（`runSyncCycle`）

```
   被推送唤醒 / 点「立即同步增量」/ 兜底定时器到点
              │
              ▼
      ┌───────────────┐
      │ 列出启用账号   │  空 → 结束
      └───────┬───────┘
              │ 有 N 个 → 顺序处理（不并发，避免触发邮箱限流）
              ▼
   ╔══════════════════════════════════════════════╗
   ║  对每个账号：                                 ║
   ║                                              ║
   ║   连中继 → 中继连 QQ → LOGIN → SELECT INBOX   ║
   ║              │                               ║
   ║              ▼                               ║
   ║      游标是空的？                              ║
   ║        ├── 是（首次同步）                      ║
   ║        │     └─▶ 只记下 UIDNEXT-1 作为游标     ║
   ║        │         拉取 0 封，结束这一轮  ★      ║
   ║        │                                      ║
   ║        └── 否（增量）                          ║
   ║              │                               ║
   ║              ▼                               ║
   ║     UIDVALIDITY 变了吗？                      ║
   ║        └── 变了 → 清零游标 + 警告，不试图恢复   ║
   ║              │                               ║
   ║              ▼                               ║
   ║     UID SEARCH UID <游标+1>:*                 ║
   ║        （只拿 UID 列表，几十字节）              ║
   ║              │                               ║
   ║              ├── 空 → 游标推到 UIDNEXT-1，结束 ║
   ║              │                               ║
   ║              └── 有 K 个 UID                  ║
   ║                    │                         ║
   ║                    ▼                         ║
   ║          取最旧的 50 个（不是最新！）★         ║
   ║                    │                         ║
   ║                    ▼                         ║
   ║          UID FETCH <批首>:<批尾>             ║
   ║                    │                         ║
   ║                    ▼                         ║
   ║          游标推进到「本批最后一个」★          ║
   ║          （不是 UIDNEXT-1）                   ║
   ║                    │                         ║
   ║                    ▼                         ║
   ║              LOGOUT，断开                     ║
   ╚══════════════════════════════════════════════╝
              │
              ▼
        逐封处理（下一节）
              │
              ▼
      重算角标 → 通知界面
```

★ 三处带星号的是**硬约束**，写错会静默丢邮件。

## 6. 积压：50 封 / 批 是怎么消化的

```
   游标 37727，服务器已有 37728…37777（积压 50 封）
   ────────────────────────────────────────────────
   第 1 批   FETCH 37728:37777      游标 → 37777
   第 2 批   SEARCH → 空            游标 → UIDNEXT-1
```

```
   积压 5000 封时
   ────────────────────────────────────────────────
   第 1 批   FETCH 37728:37777      游标 → 37777
   第 2 批   FETCH 37778:37827      游标 → 37827
    …
   第 100 批 追平
```

**关键**：游标永远只推进到「本批确实处理过的最后一个」。
任何一批失败都不丢件 —— 游标没动，下次重拉同一批。

⚠️ **一轮同步只处理一批**（≤50 封），**没有轮内循环**：
`syncAccount` 只调一次 `fetchSince`，`runSyncCycle` 只跑一次 `syncAllAccounts`。
所以积压是**由后续心跳一轮轮吃完的**，不是在某一轮里循环到追平。

（`MAX_MESSAGES_PER_SYNC = 50` 限的是**单次 FETCH 传输量** ——
一次 `UID FETCH` 拉几千封正文必然撞爆 IMAP 的 30 秒命令超时。
早期文档写「抓完一批后自己接着抓，直到 SEARCH 返回空」，那是**没实现**的。）

> 代价是追平 3 万封积压要几百轮心跳（≈ 数天）。这是可接受的：
> 用户关心的是**新**邮件 —— 而新邮件由中继推送即时触发同步，
> 积压只是历史，慢慢补即可，且补的过程中新邮件始终优先。

## 7. 兜底定时器

推送依赖「中继在跑 + 连接活着」。两个前提都可能不成立（中继没起、电脑睡眠后
连接没恢复、网络切换），所以插件保留一个**低频**的 `chrome.alarms`：

```
   每 10 分钟（**写死**，`SYNC_PERIOD_MINUTES`）
        │
        ▼
   走同一条 runSyncCycle
        │
        └─ 如果中继没在跑 → 顺手尝试重连 watch
```

它的职责从「主要收信手段」降级为「保险丝」：

- 推送正常时，它基本上每次都拉 0 封 —— **不额外打扰邮箱**；
- 推送失效时，最坏 10 分钟延迟，而不是永远收不到；
- 用户手动点「立即同步增量」随时可以立刻抓一轮。

> `chrome.alarms` 的最小间隔由 Chrome 限制（约 30 秒 / 1 分钟），
> 所以「更低频」是免费的，而「更高频」做不到。

## 8. 「同步中」是怎么结束的

```
   你点「立即同步增量」
          │
          ▼
   ① UI → background：accounts:sync-now
      ◀── 立刻返回 { started: true }           ← 不持有长消息
          │                                      （MV3 worker 30 秒会回收）
          │  ⚠️ `startedAt` 是 **UI 侧**记的（`bridge.ts`），
          │     background 只回 `started`。用它跟 `finishedAt` 比对，
          │     判断「这是不是我这次点击的结果」
          ▼
      background 在后台跑同步
          │
          ├──▶ ② 广播 sync:done    ──── 快，但可能丢
          │                              （连接时序 / 端点名对不上）
          │
          └──▶ ③ 结果存进 lastSync
                        ▲
                        │
      UI 每 1.5 秒问一次 accounts:sync-status
      （只认 finishedAt ≥ startedAt 的结果 —— 否则是上一轮的）
                        │
                        ▼
              谁先到算谁的 → busy = false
              最坏 6 分钟超时并提示
```
